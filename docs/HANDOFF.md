## 목표 (2026-10-09 사용자 결정)
- **UNICEF 0.53 / WB 0.51 / UNHCR 0.95.** v8의 13위(표시 0.65)는 만족할 결과가 아니라 실패의 일부로 본다. v8은 공개 모델을 붙인 베이스라인이다.
- **WB와 UNHCR은 별도 트랙으로 공략한다.** 상위 팀이 WB 0.50, UNHCR 0.94에 있으니 두 곳에 실제로 남은 몫이 있다.
  - UNHCR 트랙: 실데이터처럼 gate 일치도가 흔들리는 상황(중앙값 0.83, 0.29~0.98)을 실험실에서 재현하는 것이 첫 과제다. 지금 GSS 실험실은 일치도가 거의 1.0이라 이걸 못 본다.
  - WB 트랙: WB에만 있는 구조(사전 GIVEN 임금 기대 → 사후 PREDICT 임금 기대, 후속조사 참여와 `Not answered`, `group` 분기)를 아직 하나도 공략하지 않았다. WB와 비슷한 실데이터 대리 실험실도 필요하다.
  - UNICEF: 실험실 기준으로 추정의 남은 몫은 ~0.01이고, TabICL이 0.002를 가져갔다. 0.53은 남은 몫을 거의 다 가져와야 가능하다.
- **성능 자체가 NeurIPS 본 학회 수준의 novelty여야 한다.** 이론 근거가 있는 새 추정량이 여러 실제 설문에서 일관되게 이겨야 한다. 공개 모델을 붙이는 엔지니어링(v8)은 novelty가 아니다.

## 2026-10-09 갱신 (먼저 읽을 것)
**v8 Dev 결과: Grand 0.65 (0.6467) / UNICEF 0.52 / WB 0.49 / UNHCR 0.93** (submission 971475). v7은 0.6433 / 0.52 / 0.49 / 0.92였다.

이 결과를 읽을 때 피해야 할 편향:
1. **크기를 과대 해석하지 말 것.** UNHCR +0.01은 반올림 경계를 넘은 것일 뿐이다. 실제 이득은 0~0.02 사이 어디든 가능하다. 실험실 근거로는 +0.0025 안팎이 기본 가정이다.
2. **원인을 특정하지 말 것.** TabICL, 분기 분해, 결합, v7 코어 버그 수정 중 무엇이 기여했는지 이 제출로는 알 수 없다.
3. **"UNICEF·WB는 효과 없음"으로 읽지 말 것.** 0.01보다 작은 변화는 보이지 않는다.
4. **0.65를 다음 목표의 바닥으로 삼지 말 것.** 표시값 0.65는 평균 0.6467을 반올림한 것이다. 상위권(0.6533)과의 표시 격차는 WB와 UNHCR에서 각각 0.01이다.
5. **Dev 순위가 아니라 Final(단일 제출, 정확값, TRAIN+DEV 학습, 3600초)이 목표다.** 0.002 안팎의 이득이 Final의 동점 판정을 가를 수 있다.

- **합성 world 대신 공개 실데이터 실험실을 만들었다** (`docs/LAB.md`). GSS를 대회 형식으로 바꿨고, UNHCR 스키마에 문서화된 wave 기록 방식을 입힌 변형도 있다.
- 실데이터에서는 모델 계열이 달라도 0.005 안에 모인다. 학습곡선으로 외삽한 남은 추정 이득은 약 0.01이다.
- v7을 확실히 이긴 것은 **TabICLv2 하나**다(+0.002). → `sub/v8`
- 이득이 없었던 것: 모델-사전 EB 셀 보정, 선형 블렌드 개선, 다중과제 특징, 앙상블 확대, 문항별·설문 단위 미세조정(과적합)
- 다음 과제: Dev에서 v8이 실제로 손해 없이 도는지 확인. 실데이터 UNHCR처럼 gate 일치도가 흔들리는 상황은 아직 실험실에서 재현하지 못했다.
- 작업 습관 추가: `pgrep -f`/`pkill -f`로 대기 루프를 걸면 자기 셸과 매칭된다. 반드시 PID(`kill -0 $PID`)로 기다린다.
- 작업 습관 추가: GPU(3090 한 장)에 실험을 동시에 여러 개 올리지 말 것. 서로 느려지고(TabICL 72s → 683s), OOM으로 fallback이 작동해 결과가 오염된다.
- 재현: `make setup && make lab-data && make tabicl`. GSS 원자료는 해시로 검증한다(`tools/fetch_gss.sh`). 실험 캐시(`results/`)와 제출 원본 zip은 git에 없다. 백업 위치는 아래 "백업"을 볼 것.

## 1. 목표
- **내일(10-09)부터 목표는 Dev 리더보드 1등이다.** 상위권과 같은 점수를 내는 것은 목표가 아니다. 모든 팀이 멈춘 지점을 뚫는 것이 목표다.

## 4. 내일 할 일 (1등 기준)
1. **UNHCR 0.92 → 0.94 이상.** 다른 팀이 이미 도달했으니 실데이터에 존재하는 이득이다. 가장 확실한 레버다.
   - **wave별 sentinel 코딩:** round 1에서 건너뛴 응답자는 "0", round 2는 NA_GATED로 기록된다. 확인할 것: `_cond_eb`와 gate 분해(`gate_factor`)가 wave와 부모 응답의 상호작용을 실제로 쓰는가? 지금은 GIVEN 열을 MI 순위로 고르기 때문에 wave가 빠질 수 있다.
   - **gate 신뢰도 0.29~0.98:** 문항별로 과신하는지 진단한다. 스키마 설명에 문항별 일치도가 있는지 확인하고, 있으면 사전정보로 쓴다.
   - **다중선택 가족:** `s7a_7_reason_*`, `s6_11_challenge_*` 등이다. 같은 부모 아래의 이진 문항들이 정보를 공유하게 만든다.
   - 그다음: 스키마에서 확인되는 사실(일치도, wave 코딩, 가족 구조)로 UNHCR 전용 world를 만들고 `tools/headroom.py`로 손실 위치를 분해한다.
2. **계산 여유 활용:** fold·seed bagging과 MLP 다양화로 분산을 줄인다. 예산 적응형 구조로 만든다(STRATEGY.md §2). 동점 판정(paired bootstrap)에서도 유리하다.
3. **WB 0.49 → 0.50 이상:** 상위권은 0.50이다. 진단 질문은 "sint가 실데이터 WB에서 손해인가?"이고, v4와 v7을 비교하면 답할 수 있다.
4. **제출 선택은 사용자가 정한다.** 프로토콜은 "제출 하나에 질문 하나"다. 그런데 1등이 목표면 검증된 변경을 묶어 내고 싶을 수 있다. 묶을 때는 변경 각각의 내부 증거를 기록하고, 무엇을 묶었는지 제출 기록에 남긴다.

## 5. 다음 세션 AI를 위한 주의사항 (편향 방지)
1. **합성 데이터 낙관 편향.** 이번 세션의 가장 큰 교훈이다. 우리가 만든 world에서 찾은 빈틈은 우리가 그 구조를 넣었기 때문일 수 있다(순환성). v7은 9개 생성기에서 이겼지만 실데이터 WB에서는 지지 않았을 뿐 이기지도 못했다. 실데이터 근거는 Dev 점수뿐이다. 합성 결과는 "손해가 없다"는 안전성 증거로만 쓴다.
2. **"천장" 프레이밍 금지.** 리더보드 정체(UNICEF 0.52, WB 0.50)나 합성 오라클을 한계로 단정하지 말 것. 사용자가 명시적으로 거부했다. 오라클 headroom은 시뮬레이터가 너무 쉬운지 진단하는 데만 쓴다.
3. **이전 AI의 결론에 고정되지 말 것.** 이 문서와 EXPERIMENTS.md도 틀릴 수 있다. 이번 세션에서 틀린 주장이 실제로 여러 번 나왔다.

   - "embedding_bag이 60배 빠를 것" → 오히려 느렸다.
   - "순서형이 놓친 핵심" → 이득이 작았다.
   - "시간이 부풀려진 건 GPU 경합 때문" → UNHCR은 실제로 무거웠다.
   
   주장은 돌려서 확인하고, 틀리면 틀렸다고 쓴다.
