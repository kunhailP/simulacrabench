# Dev 제출 프로토콜

Dev 제출은 하루 1회다. 남은 횟수는 약 37회이고, 실데이터 신호는 이것뿐이다. 그래서 **모든 제출은 사전등록한 실험**으로 다룬다. 제출 전에 이 양식을 채우고, 리뷰어(kunhailP)가 승인해야 업로드한다.

## 해상도의 한계 (계산값, RESEARCH.md §3)
- Dev 점수는 기관별 정확값을 0.01로 반올림한 값이다. Laplace 노이즈 표준편차는 ≤ 0.0013으로 무시할 수 있다.
- 따라서 **기관별 차이가 0.005 미만인 변경은 리더보드로 판정할 수 없다.** 그런 변경은 제출하지 않고 내부 CV로만 판정한다.
- 제출 하나로 질문 **하나**만 묻는다. 두 가지를 한꺼번에 바꾸면 무엇이 효과를 냈는지 알 수 없다.
- DEV 표본 크기 기준 표준오차 (sim2 기준 근사): UNICEF ≈ 0.004, WB ≈ 0.003, UNHCR ≈ 0.005. 이는 Test 단계에서 다른 팀과의 차이를 판정할 때 의미가 있다(paired bootstrap 동점 규정).

## 제출 양식 (`docs/submissions/YYYY-MM-DD.md`)

```
# 제출 YYYY-MM-DD — <버전>
## 질문 (하나)
<예: EB 수축이 고정격자 backoff보다 실데이터 UNICEF에서 낫다>
## 이전 제출과의 차이 (diff 요약, commit hash)
## 예상 (사전등록)
- 방향: UNICEF ↑ / WB = / UNHCR =
- 근거: 내부 CV 결과, 시나리오 S1..Sn에서의 결과
- 이 결과가 나오면 결론 A, 반대면 결론 B (판정 규칙을 미리 적는다)
## 사전 점검
- [ ] make zip OK
- [ ] make official 3/3 PASS (phase 1), phase 2 PASS
- [ ] 총 시간 (3090) ___ s, 예상 H100 ___ s, 한도 900 s의 60% 이하
- [ ] 모든 시나리오에서 marginal 대비 손해 없음
- [ ] 리뷰어 승인: ___
## 결과 (제출 후 기입)
Grand / UNICEF / WB / UNHCR, 판정, 다음 행동
```

## 무엇을 제출로 확인할 가치가 있는가
1. **실행 환경 위험** (Python 3.12/3.13, H100, torch 버전): 첫 제출의 목적이다.
2. **sim2와 실데이터의 괴리를 드러낼 질문:** 모델군 가중치, GIVEN 정보량, gate 신뢰도처럼 합성 데이터로는 답할 수 없는 것.
3. 기관별 0.01 이상 움직일 것으로 예상되는 변경만 제출한다.
